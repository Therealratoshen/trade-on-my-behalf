# Roadmap — Readiness Gates Rather Than Assumed Dates

Updated 2026-10-03. Earlier day-number schedules were targets, not proof of delivery.

| Gate | Deliverable | Current state |
|---|---|---|
| R0 | Consistent product/technical/test documentation and truthful claims | Documentation revision; not runtime fixes |
| R1 | Exact numeric/network/identity checks, isolated storage and reliable audit recovery | Gaps identified; implementation pending |
| R2 | Treasury build/IDL validation and verified devnet deployment | Configured address absent at dated check |
| R3 | Select one current supported devnet venue and demonstrate test funding/market/order/close | Selection OPEN; program existence only observed |
| R4 | App-account custody/authority binding, verifiable risk and durable intent journal | Not implemented |
| R5 | One wallet + SOL-PERP chart + ticket + account-scoped positions/receipts terminal | Chart/ticket/real lifecycle not implemented |
| R6 | Unit/local/browser/devnet checks and three outside-user sessions with actual evidence | Existing source cases; new plans; sessions NOT RUN |
| R7 | Accurate videos, receipts, link check and event submission | No new completion claim |

Budget semantics/visibility and on-chain CI are separate already-scoped work; documentation does not implement them. Do not silently defer a release-critical bypass to “post-launch hardening.”

If time/venue support blocks real execution, narrow the release honestly to a **policy demo with paper positions**. Cut additional venues, autonomous strategies, messaging, billing and social features before removing safety, ownership or truthful-mode requirements.

[PRD](../PRD.md), [TRD](../TRD.md) and [testing status](testing-plan.md) define release acceptance.
